# 통화 차단 지연: 2026-11-15 로컬 검토

최신 통화 기본 API와 연결 확인 결과, 고정 지연 버퍼에서 확인한 첫 공격 음성 전달 문제는 [Gemini 전환 상태](GEMINI-PHONE-STATUS.md)를 참고한다. 아래 표는 이전 OpenAI 경로의 후보 실험이며 Gemini 성능 수치가 아니다.

최초 실험은 운영 코드를 수정하지 않고 같은 실제 API와 재연 음원으로 계측했다. 아래 후보 실험은 `cad3680` 기준 연구용 프로토타입이다. 이후 사용자가 단어 목록 조건 제거를 지시하여 현재 구현을 변경했다. 샘플과 결과는 저장소 밖 `../phone-licensed-check/`에 보관한다.

기존 경로에서 최초 전사 델타는 음원 시작 0.97초, 첫 공격 표현의 전사는 5.20초였으나, `needsSafetyCheck` 목록이 처음 맞은 7.77초에야 조기 판정을 시작했다. 그 판정이 2.16초 후 완료되어 9.93초에 보호 신호를 냈다. 해당 입력의 앞선 공격 표현이 목록에 없어서 생긴 지연이다. 모델은 이미 실시간 전사인 `gpt-live-transcribe`를 쓰므로 단순히 실시간 모델로 바꾸자는 제안은 적절하지 않다.

| 로컬 후보 | 음원 시작→보호 | 기록된 파이프라인 HTTP 호출 |
| --- | ---: | ---: |
| 기존 low·단어 목록에 따른 조기 검사 | 9.93초 | 4 |
| low·새 부분 문장 문맥 검사 | 7.29초 | 7 |
| minimal·새 부분 문장 문맥 검사 | 7.04초 | 7 |

후보는 검사 간격 최소 1.2초, 부분 검사 동시 실행 1개, 부분 문장 8자 이상을 사용한다. 최종 판정과 발췌 검사는 같은 `checkSafety`를 사용하며 단어 목록으로 차단 여부를 결정하지 않는다. 최초 minimal 프로토타입은 공백만 있는 부분 입력까지 검사한 문제가 있었고, 이를 수정한 뒤 재실행한 결과가 표의 7.04초다. 선행 결과(7.00초)도 보관한다. latency 설정과 네트워크·모델 응답 변동의 효과를 분리한 통제 실험이 아니며 평균·p95·SLA가 아니다. HTTP 호출 수는 실시간 전사·원음 재검토를 제외하므로 비용 비교를 대신하지 않는다.

minimal 후보에서 기관 정리 정상 민원 1개와 제3자 공격 댓글 1개는 차단하지 않았다. 피해 신고·인용·잡음·억양을 포함한 전체 오차단 평가는 아니다. low 후보에서는 공격만 있는 입력을 정제한 결과에 공격 의미를 순화한 문장이 사실로 남았다. 이 정제 품질 실패도 기록한다. low 설정의 인과 효과라고 단정하지 않으며, 조기 판정 개선을 운영 반영하기 전에 정제 회귀 사례를 보강해야 한다.

추천 순서는 부분 문장 기반 조기 판정 → 빠른 보호와 최종 재전사·정제의 경로 분리 → 실제 마이크 검증이다. 최초 공격 음성까지 가리려면 수신 음성을 판단 시간만큼 지연하는 버퍼가 필요하지만 대화 지연이 늘어난다. 버퍼 1~2초는 검증하지 않은 후보이며 충분한 차단을 보장하지 않는다. 실제 공격 발화·전사·판정·브라우저 재생의 시점을 계측한 뒤 선택해야 한다.

공식 근거: [Realtime transcription](https://developers.openai.com/api/docs/guides/realtime-transcription)은 `minimal`부터 `xhigh`까지 지연/품질 조절과 실제 음성 평가를 안내한다. [VAD](https://developers.openai.com/api/docs/guides/realtime-vad)에 따르면 현재 전사 모델은 `turn_detection:null`을 사용하므로 무작정 server VAD로 바꾸지 않는다. [Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)은 계측 후 독립 단계 병렬화와 불필요한 순차 호출 제거를 권고한다.

## 단어 목록 제거 후 구현

- 모든 비어 있지 않은 STT 델타가 부분 문맥 판정 대상이다. 단어 목록과 발화당 3회 조기 검사 상한을 제거했다. 표시용 단어 마스킹은 남아 있지만 검사를 시작하거나 차단 여부를 결정하지 않는다. 과거 `evals/phone-handoff/` 실험 사본과 운영 경로를 구분한다.
- `phone/live-safety.mjs`는 통화당 부분 검사 1개만 실행하며, 진행 중 새 델타는 발화별 최신 문장으로 합친다. 첫 요청은 즉시 시작하고 후속 요청 시작 간격은 기본 최소 1,200ms다. 실제 AI 응답이 더 느리면 응답이 끝나야 다음 요청을 시작한다. `PHONE_SAFETY_INTERVAL_MS`는 호출 정책이며 차단 시간을 보장하지 않는다.
- 부분 문장임을 모델 입력에 명시하고, 발화자·공격 대상·문맥 및 실제 원문 발췌를 검증한다. 인용·피해 신고·업무 비판을 직접 공격으로 확정하지 않는다. 아직 나오지 않은 후속 문맥까지 보장하는 방식은 아니다.
- 최종 재전사 후 보호 판정과 업무 사실 추출을 병렬로 시작한다. 원음 재검토는 단어 일치 대신 문맥 판정 불확실·실패 시 실행하며 빠른 보호 판정 앞에서 기다리지 않는다. 최종 판정 시작 시 오래된 부분 요청을 취소하고, 통화 종료 후 도착한 판정은 차단 동작을 만들지 않는다.
- 기존 공격 의미 잔존 오류를 재현했다. 업무 사실 후보를 별도 AI 호출로 역할 검사하며, 순화된 직접 공격은 제외한다. 모든 후보 ID가 정확히 한 번 검토되어야 하고, 근거 없는 사실·불명확한 역할은 성공 요약으로 숨기지 않는다. 이 검사는 보호 판정 경로를 막지 않는다. 제3자 피해·보호 요청·정당한 업무 요구는 보존한다.

현재 구현의 로컬 실제 API 공격 음원 측정은 시작→보호 8.06초, 정제 검증 보강 후 재측정은 8.54초였다. 후자의 공격 전용 입력은 facts=[]이며 분석 오류가 없었다. 첫 측정의 공격 의미 잔존 실패도 원본 결과에 남긴다. 앞선 프로토타입의 7.04초를 현재 구현의 확정 성능으로 사용하지 않는다. 처음 공격이 들린 시점이나 평균·최악 지연을 뜻하지 않으며 실제 마이크 검증은 남아 있다.

현재 코드 재현: `node --env-file=.env.local scripts/profile-phone-latency.mjs --live --mode=current --sample=attack` (`normal`, `thirdparty`도 가능). 과거 `baseline`/`partial-*` 모드는 `cad3680`에서만 재현한다. 프로파일 스크립트 자체는 운영 중계를 변경하지 않는다.
