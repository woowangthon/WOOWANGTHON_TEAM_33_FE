# 시민 요구 확인과 요구별 처리 검증

2026-11-08. 시민은 접수 후 요구사항을 확인·수정·추가하거나 철회할 수 있다. 담당자는 각 요구의 실제 처리 상태를 별도로 기록한다. 접수 원문과 최초 요구 문구, 변경 이력은 보존한다.

## 구현과 상태 규칙

- 시민 화면: 나의 민원 → 상세 → 요구사항 확인 및 처리 현황. 확인은 선택 사항이며 접수를 막지 않는다.
- 담당자 화면: 민원 상세 → 요구별 처리 현황. 접수, 추가 정보 대기, 처리 중, 처리 완료, 처리 불가를 구분한다. 상태 변경에는 시민에게 표시되는 설명이 필요하다.
- 추가 정보 대기인 요구에 시민이 답하면 해당 요구만 접수 상태로 돌아가며 분석을 다시 예약한다.
- 요구 수정은 기존 완료 상태를 다시 열고 이전 요약·답변 검증을 무효화한다. 다른 요구의 완료 기록은 유지한다.
- 답변 등록이나 AI 재분석은 요구를 자동 완료하지 않는다. 완료는 담당자가 결과를 기록해 결정하며 실제 현장 조치의 진위를 시스템이 자동 입증하지는 않는다.
- 확인된 요구는 고정 ID로 검사한다. 모델이 항목을 누락하거나 원문 인용을 바꾸면 해당 항목을 확인 필요로 유지한다. 수정 전 요구와 철회한 요구를 현재 목록에 자동 복원하지 않는다.
- DB 수정은 민원 소유권, 담당자 권한, 현재 revision, 삭제 여부를 확인한다. 요구 변경 시 이전 분석 세대의 저장도 차단한다.

## 새 합성 평가셋

[12개 사례](../evals/request-tracking-12.json)는 기존 40개 사례와 별개다. 폐기물, 소음, 교통, 공원, 배수, 보행, 도서관, 가로수, 복지, 동물, 주차, 정보공개 상황에 각 3개 요구를 넣었다. 독립적인 사람이 작성·검수한 정답은 아니며 개발 중 작성한 합성 평가다.

각 사례에서 첫 두 요구만 포함한 요약을 고정했다. 먼저 원문 3개 요구의 추출·요약 누락을 검사했다. 그다음 시민 수정 동작을 스크립트로 적용했다. 두 번째 요구의 날짜·대상·조건을 바꾸고, 세 번째 요구를 철회하고, 새 요구를 추가했다. 수정 후에도 활성 요구는 사례당 3개다. 실제 시민을 대상으로 한 사용성 실험은 아니다.

실제 서비스 모델 `gpt-6-luna`를 24회 호출했다. 정답 판정과 평가 사례 ID는 제품 호출에 전달하지 않았다. 원본 입력과 평가 코드·제품 코드의 SHA-256, 모델 출력, API 토큰 사용량을 [실행 결과](../evals/results/request-tracking-12.json)에 저장했다.

수정 전은 보존 24개·누락 12개, 수정 후는 보존 12개·누락 또는 의미 변경 24개를 구분하는 검사다. 서로 다른 요구 버전을 비교하므로 동일 입력에서 정확도가 상승했다는 전후 비교로 사용하지 않는다. 단순하고 명시적인 문장으로 구성된 소규모 평가이며 기존 40건에서 남은 오경보 8개가 해결됐다는 뜻도 아니다. 법령 검색·초안 생성 전 과정을 이 12건으로 다시 실행한 결과는 아니다.

## 기능 및 데이터 검증

- 단위 테스트 96개, 음성 프로토콜·필터 테스트 20개 통과. 새 12개 시나리오에서 ID·원문·이력 보존, 철회, 개별 상태 변경, 추가 정보 후 재개, 잘못된 완료 처리 방지를 검사했다.
- 실제 PostgreSQL/API 통합 검증 9개 항목 통과: 시민용 정보 노출 범위, 원문·이력 보존, 다른 시민 접근 차단과 담당자 권한, 동시 수정 충돌, 보완 후 재분석 예약, 답변 등록과 실제 처리의 분리, 선택한 요구만 완료, 완료 후 수정 시 재개, 삭제 민원 변경 차단.
- 통합 검사의 모델과 Workflow 발송은 모의했다. [통합 검증 결과](../evals/results/request-tracking-integration.json).
- 기존 보완·사진·복구·체크포인트·담당자 수정 보존 DB 통합 검증 통과. TypeScript와 운영 빌드 통과.

## 운영 사이트 연결 검증

2026-11-08 시민 사이트와 담당자 사이트에 배포했다. 별도의 합성 민원 1건을 실제 시민 화면으로 접수하고, 실제 OpenAI·법령 조회·Workflow를 거쳐 다음 흐름을 확인했다. 이 검사는 위 12건 평가와 구분한다.

1. 시민이 두 번째 요구를 월요일 수거 일정으로 수정하고, 세 번째 요구를 철회하고, 담당 부서 연락처 요구를 추가했다. 담당자 화면에도 같은 목록이 표시됐다.
2. 담당자가 첫 번째 요구만 추가 정보 대기로 바꿨다. 시민이 그 요구에 답변하자 해당 요구만 다시 접수 상태로 전환되고 재분석이 실행됐다.
3. 담당자가 첫 번째 요구에 합성 처리 결과를 기록했다. 재분석 완료 후에도 활성 요구 3개, 처리 완료 1개, 진행 중 2개와 철회 이력이 유지됐다. 원문은 그대로였으며, 요구별 검사에는 활성 요구의 고정 ID 3개만 포함됐다.
4. 실제 법령 검색 후보 3개가 반환됐고 최신 분석 세대가 완료됐다. 확인한 것은 연결 및 상태 보존이며, 검색 결과 전체의 법적 타당성을 별도로 평가한 것은 아니다.

[운영 연결 검증 결과](../evals/results/request-tracking-live.json)와 [시민 화면](assets/request-tracking-citizen.jpg)을 보관했다. 검증용 완료 기록은 실제 현장 조치가 아니다. 테스트 민원은 운영 API로 복구 가능한 휴지통에 옮겼으며 다른 민원은 변경하지 않았다.

## 재현

```sh
node --test tests/request-tracking.test.cjs
node --env-file=.env.local tests/request-tracking.integration.cjs
# 실제 유료 AI 호출: 새 결과 파일 경로를 지정하거나 동일 입력·코드의 실패 단계만 재개
node --env-file=.env.local evals/run-request-tracking.cjs
```

평가 스크립트는 변경된 입력·코드로 기존 결과를 덮어쓰지 않는다. 재평가 시 `TRACKING_EVAL_OUT`에 새 파일 경로를 지정한다.
